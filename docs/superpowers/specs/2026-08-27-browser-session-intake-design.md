# 브라우저 세션 투입 — 설계

**상태:** 승인됨 (2026-08-27)
**선행 스펙:** `2026-08-26-unlabelled-session-explorer-design.md`
**전제:** 선행 스펙의 `add-session` / `run` / `explore` 경로는 구현·검증 완료

---

## 1. 목적

유튜브 URL이나 오디오 파일을 **브라우저에서** 넘기면 파이썬 백엔드가
`add-session → run → explore`를 대신 돌린다. 터미널로 돌아갈 일을 없앤다.

### 왜 서버가 필요한가

지금 탐색 페이지는 서버 없는 정적 HTML이다. 브라우저 샌드박스 안에서는
파일시스템에 쓸 수도, `yt-dlp`를 실행할 수도 없다. 입구를 브라우저로 옮기려면
로컬 서버가 있어야 한다. 새 의존성은 없다 — 표준 라이브러리 `http.server`로
충분하고, 어차피 한 대의 컴퓨터에서만 도는 도구다.

### 왜 엔드포인트가 하나로는 안 되는가

45분 녹음에 10개 모델을 돌리면 다운로드 몇 분에 추론 수십 분이다. 동기 요청
하나로 처리하면 브라우저가 먼저 끊기고, 끊긴 뒤에도 백엔드는 계속 돌아 무슨
일이 벌어지는지 알 수 없게 된다. 그래서 **작업을 만드는 요청**과 **상태를 묻는
요청**이 따로 있어야 한다. 이 둘이 최소치다.

---

## 2. 범위

**들어가는 것:** 세션 투입(URL/파일), 모델 선택, 진행 표시, 결과 링크.

**들어가지 않는 것:**

- 탐색 페이지 자체의 변경 — 결과를 보는 화면은 선행 스펙 그대로다
- 세션 목록 관리, 삭제, 재실행 — 필요해지면 별도 스펙
- 라벨 찍기 — 여전히 범위 밖
- 원격 접근·인증 — § 6 참조

기존 CLI 명령은 전부 그대로 남는다. `serve`는 추가일 뿐 대체가 아니다.

---

## 3. 구성 요소

새 모듈 둘, 기존 코드 수정 하나.

| 파일 | 책임 |
|---|---|
| `bandpoc/jobs.py` | 작업 큐와 상태 전이. **HTTP를 모른다** |
| `bandpoc/server.py` | 라우팅, 요청 파싱, 정적 서빙. **파이프라인을 모른다** |
| `bandpoc/cli.py` | `serve` 서브커맨드 추가 |

경계를 이렇게 그으면 `jobs.py`는 HTTP 없이 테스트할 수 있고, `server.py`는
가짜 작업 큐로 테스트할 수 있다.

### 3.1 작업 큐 — `bandpoc/jobs.py`

```python
@dataclass
class Job:
    job_id: str
    session_id: str | None
    source: str            # URL 또는 로컬 경로
    detectors: tuple[str, ...]
    state: str             # queued | running | done | failed
    log: list[str]
    report_url: str | None
    error: str | None
```

```python
class JobQueue:
    def submit(self, source: str, detectors: Sequence[str],
               session_id: str | None = None) -> Job: ...
    def get(self, job_id: str) -> Job | None: ...
    def recent(self, limit: int = 20) -> list[Job]: ...
```

**큐는 직렬이다.** 워커 스레드 하나가 한 번에 한 작업만 처리한다. 동시에 두
세션을 추론하면 모델이 두 벌 로드된다 — PANNs 체크포인트만 327MB이고, 45분
세션 하나가 이미 RAM을 크게 쓴다. 대기 중인 작업은 `queued`로 보인다.

**작업 하나가 하는 일**은 선행 스펙의 세 단계를 순서대로 부르는 것뿐이다:
`session.add_session` → `cmd_run`에 해당하는 추론 → `cmd_explore`에 해당하는
렌더. 파이프라인을 재구현하지 않는다.

**진행 로그는 기존 `print`를 가로챈다.** `cmd_run`은 이미
`[done] s x panns_cnn14:music_group  RTF=0.0421  RSS=1802MB` 같은 줄을 찍는다.
`contextlib.redirect_stdout`으로 그 출력을 `Job.log`에 모은다. 새 진행 보고
체계를 만들지 않는다 — CLI가 보여주는 것과 정확히 같은 내용이 페이지에 뜬다.

**상태는 메모리에만 있다.** 서버를 재시작하면 작업 이력은 사라진다. 산출물
(`data/scenes/`, `data/cache/`, `reports/`)은 디스크에 남으므로 잃는 것은
로그뿐이다. 작업 이력을 영속화할 이유가 아직 없다.

### 3.2 HTTP — `bandpoc/server.py`

`ThreadingHTTPServer` + `BaseHTTPRequestHandler`. 기본 포트는 **8765**이고
`--port`로 바꿀 수 있다. 포트가 이미 쓰이고 있으면 다른 포트를 쓰라는 안내와
함께 종료한다 — 조용히 다른 포트로 옮겨가면 어디에 붙어야 할지 알 수 없다.

```
GET  /                  폼 페이지
POST /api/sessions      작업 생성 -> 202 {"job_id": "..."}
GET  /api/jobs/<id>     {"state","log","report_url","error","session_id"}
GET  /api/jobs          최근 작업 목록
GET  /api/detectors     등록된 키 목록 (체크박스를 채운다)
GET  /reports/...       탐색 페이지와 mp3 정적 서빙
```

**`POST /api/sessions`는 두 가지 몸통을 받는다.**

- `Content-Type: application/json` — `{"url": "...", "detectors": [...], "id": "..."}`
- 그 외 — 요청 몸통 전체가 파일 바이트, 파일명은 `X-Filename` 헤더,
  모델 선택은 `X-Detectors` 헤더(쉼표 구분)

**multipart를 쓰지 않는다.** 표준 라이브러리의 `cgi`는 3.13에서 제거됐고 3.11에서
이미 deprecated다. 직접 파싱하는 코드는 그 자체가 공격면이며, 이 프로젝트는
파싱 가정이 틀려서 생긴 구멍을 이미 한 번 냈다(`?v=../../evil`). raw body에
헤더 하나면 파싱할 게 없다.

**업로드 상한은 1GB다.** 45분 48kHz 모노 wav가 259MB이므로 3시간짜리 세션도
들어가고, 오타나 잘못된 요청이 디스크를 채우는 것은 막는다. 초과하면 413.
`Content-Length`를 먼저 보고 거절하므로 상한을 넘는 몸통을 읽지 않는다.

**업로드의 세션 id는 폼의 id 칸에서 온다.** 비어 있으면 `X-Filename`의 확장자
없는 부분을 slug해서 쓴다. `X-Filename`은 그 용도와 확장자 판별에만 쓰이고
저장 경로에 직접 들어가지 않는다.

### 3.3 폼 페이지

한 화면에 셋:

1. **투입** — URL 입력칸, 파일 드롭 영역, 모델 체크박스, 제출 버튼
2. **진행** — 실행 중인 작업의 상태와 로그 (폴링)
3. **최근 작업** — 완료된 것은 탐색 페이지로 링크

폴링은 `GET /api/jobs/<id>`를 **2초 간격**으로 부르고, 작업이 `done`이나
`failed`에 닿으면 멈춘다. SSE나 WebSocket을 쓰지 않는다 — 폴링으로 충분하고,
재연결 처리가 통째로 사라진다. 추론이 수십 분 걸리는 작업에서 2초 폴링의
비용은 무시할 만하다.

모델 체크박스의 기본 선택은 **빠른 것들**(`dsp_baseline`, `panns_cnn14`,
`yamnet`)이다. AST와 CLAP은 창을 겹쳐 미는 구조라 훨씬 느리므로 켜고 싶을 때만
켠다. 각 항목에 대략의 속도를 표시해 무엇을 기다리게 되는지 알 수 있게 한다.

## 4. 데이터 흐름

```
브라우저 ─ POST /api/sessions ─→ JobQueue.submit ─→ 202 {job_id}
                                       │
                                  (워커 스레드, 직렬)
                                       │
                          add_session ─→ run ─→ explore
                                       │         │
                                   stdout 캡처   reports/explore/<stamp>/

                                                 │
브라우저 ─ GET /reports/... ─────────────────────┘
```

## 5. 실패 처리

작업 하나가 죽어도 서버는 살아있고, 그 작업만 `failed`에 이유가 붙는다. 선행
스펙이 이미 실패를 종류별로 구분해두었으므로 그대로 표면화하면 된다:

| 상황 | 지금 나는 것 | 페이지에 보일 것 |
|---|---|---|
| ffmpeg 없음 | `RuntimeError` | 설치 안내 |
| 중복 세션 id | `SessionExists` | 다른 id를 쓰라는 안내 |
| id 유도 불가 | `ValueError` | `--id`에 해당하는 입력을 채우라는 안내 |
| 다운로드 실패 | `RuntimeError` | 원문 그대로 |
| 모델 키 오타 | 이미 키별 진단 | 그대로 |

워커 스레드는 어떤 예외도 밖으로 흘리지 않는다. 예상 못 한 예외는 `failed`에
타입과 메시지를 담고 traceback은 서버 콘솔에만 남긴다.

## 6. 보안 — 로컬 전용

이건 **임의 URL을 다운로드하고 임의 경로에 파일을 쓰는 서버**다. 다음을 지킨다:

- `127.0.0.1`에만 바인딩한다. `--host` 옵션을 **두지 않는다** — 존재하지 않는
  옵션은 잘못 쓸 수 없다.
- `/reports/` 정적 서빙은 경로 traversal을 막는다. 요청 경로를 `resolve()`한 뒤
  리포트 루트 아래인지 확인하고, 아니면 403. 심볼릭 링크로 벗어나는 것도 같이
  막힌다.
- 세션 id는 선행 스펙의 slug 규칙을 그대로 통과시킨다. 유튜브 id는
  `[A-Za-z0-9_-]` 검증을 이미 거친다.
- 업로드 파일명은 신뢰하지 않는다. `X-Filename`은 확장자를 얻는 데만 쓰고,
  저장 경로는 slug된 세션 id로 만든다.
- CSRF나 인증은 두지 않는다. localhost 전용이고 단일 사용자 도구다. README에
  "이 서버를 네트워크에 노출하지 말 것"을 명시한다.

## 7. 테스트 전략

| 대상 | 검증 |
|---|---|
| `JobQueue` | 직렬 실행(두 작업이 겹치지 않음), 상태 전이, 실패한 작업이 큐를 막지 않음, 예외가 워커 밖으로 새지 않음 |
| 로그 캡처 | 파이프라인의 `print`가 `Job.log`에 들어감 |
| `POST /api/sessions` | JSON 몸통, raw 파일 몸통, 잘못된 JSON, 상한 초과(413), 모델 미선택 |
| `GET /api/jobs/<id>` | 없는 id는 404, 상태가 실제로 진행됨 |
| `/reports/` 서빙 | 정상 파일, `../` traversal 차단, 리포트 루트 밖 절대경로 차단 |
| 폼 페이지 | 렌더됨, 외부 요청 없음 (탐색 페이지와 같은 기준) |
| CLI | `serve`가 뜨고 `127.0.0.1`에만 바인딩됨 |
| 통합 | 짧은 로컬 wav로 투입 → 완료 → 리포트 URL이 실제 파일을 가리킴 |

**네트워크를 타는 테스트는 없다.** 유튜브 다운로드는 선행 스펙과 같이
`subprocess.run`을 가로채 검증한다.

## 8. 완료 기준

1. `bandpoc serve`가 뜨고 브라우저에서 폼이 보인다
2. 유튜브 URL을 넣으면 작업이 만들어지고 즉시 응답이 온다
3. 오디오 파일을 드롭하면 같은 작업이 만들어진다
4. 체크한 모델만 돌아간다
5. 진행 로그가 CLI와 같은 내용으로 페이지에 흐른다
6. 완료되면 탐색 페이지 링크가 뜨고, 눌러서 오디오가 재생된다
7. 작업 하나가 실패해도 서버가 죽지 않고 이유가 보인다
8. 두 작업을 연달아 넣으면 하나씩 처리된다
9. `/reports/../` 류 경로가 403으로 막힌다
10. 기존 CLI 네 명령이 그대로 동작한다
11. 전체 테스트 통과
